# 3Dプリントで理解するDocker基礎講座：対照ガイド＆コンセプト集

本ドキュメントは、Dockerの基本概念および周辺用語を、**「3Dプリントで構築するセット空間」**という物理的なアナロジー（例え）を用いて直感的に理解・説明するための学習・教材用ガイドです。

---

## 1. 全体像とコア・コンセプト

Dockerの各コンポーネントは、**「指示書 $\rightarrow$ 3Dデータ $\rightarrow$ プリントされた実体（空間）」**という自然な生成プロセスに完璧に対応しています。

【Dockerfile】                【Image】                      【Container】
セットの組み立て指示書  --->   完成版3Dデータ（パッケージ）  --->  プリントされたセット空間
(テキストの設計コード)         (静的・変更不可のデータ)            (中で仕掛けが動く実体)


* **指示書（Dockerfile）に従って作られる成果物は、直接的には「3Dデータ（Image）」である**という論理的整合性を保っています。
* **コンテナ（Container）は単なる物体ではなく「隔離された空間全体」**であり、その内部でプログラム（Process）が稼働します。

---

## 2. Docker用語対照表（要約）

| Dockerの概念 | 3Dプリントセットでの例え | 役割・本質的な解説 |
| :--- | :--- | :--- |
| **Dockerfile** | **セットの組み立て指示書** | テキストで書かれた構築手順・構成コード |
| **Image** | **完成版3Dデータ（パッケージ）** | 指示書に従い合成された、変更不可の静的ファイル |
| **Container** | **プリントアウトされたセット空間** | 3Dデータから実体化された、独立した実行環境（部屋） |
| **Process** | **セット内で動く「からくり・仕掛け」** | セットの中で実際に計算や処理を行っているプログラム |
| **Memory** | **からくりが作業する「作業台」** | 一時的なデータを広げる領域（電源オフで消滅） |
| **Storage** | **セット壁面の「作り付けの棚」** | セット内部の記憶領域（セット破壊とともに消滅） |
| **Volume Mount** | **壁の穴から外へ繋がる「巨大金庫」** | セットを破壊・撤去しても無傷で残る外部記憶領域 |
| **Port Mapping** | **セットの壁の「専用インターホン」** | 隔離されたセット内部へ外の世界からアクセスする窓口 |
| **Environment Variable**| **壁に貼る「本日の営業指示ボード」** | 起動時に外部から与える設定値（メモ） |
| **Network** | **セット同士を繋ぐ「専用糸電話」** | 隔離されたセット同士が安全に直接会話する通信網 |
| **Container Registry**  | **3Dデータの共有Webサイト** | 世界中の人が作った Image（3Dデータ）の保管・共有場所 |
| **Docker Compose** | **テーマパークの「一括起動プラン」** | 複数のセットや接続関係を1コマンドで一括自動構築 |
| **Multi-stage Build** | **「足場」を取り除いてデータ化する手法** | 開発用の巨大工具を除外し、Imageサイズを極小化する手法 |

## 3. 各概念の詳細解説とロジック

### ① Dockerfile $\rightarrow$ Image $\rightarrow$ Container（生成のライフサイクル）

* **Dockerfile（セットの組み立て指示書）**
  * 「ベースにOSを用意する」「必要なライブラリを追加する」「アプリのコードを配置する」といった手順がテキストで書かれたレシピ。
* **Image（完成版3Dデータ）**
  * 指示書（Dockerfile）に従って生成された完成データ。静的かつ変更不可（イミュータブル）。データなので単体では動作しないが、これがあれば誰でも全く同じ環境を一瞬で復元できる。
* **Container（プリントアウトされたセット空間）**
  * 3Dデータ（Image）をもとにメモリ上に実体化された「部屋」。この中でアプリが実際に稼働する。1つのImageから何個でも同じContainerを出力可能。

### ② コンテナ内部のリソース（Process / Memory / Storage）

* **Process（セット内で動く仕掛け・からくり）**
  * 空間（Container）の中で動いているプログラム本体。
* **Memory（可動用作業台）**
  * からくり（Process）が一時的にパーツやデータを広げる作業スペース。コンテナ停止で初期化される（揮発性）。
* **Storage（作り付けの棚）**
  * セットの壁（Containerのファイルシステム）に直接作り付けられた棚。データを保存できるが、**コンテナ自体を破棄すると棚ごと消滅する**（非永続性）。

> **訳注（からくり）**: 「からくり」は単なる抽象的な「機構・メカニズム」ではなく、歯車やゼンマイなど内部の仕掛けによって**自律的に動く人形・自動人形（からくり人形）**というニュアンスを持つ言葉。英訳する際は "mechanism" のような無機質な訳語では意味が伝わらない。"automaton"（自動人形。内部の仕掛けで自ら動く人形・機械仕掛けの存在）のように、それ自体が動いて仕事をする小さな人形・機械という含みを残せる語を使うこと。

### ③ データ永続化と外部接続（Mount / Port Mapping / Network）

* **Volume Mount（壁の穴から繋がる外部金庫）**
  * コンテナの使い捨て（イミュータブル）という性質を補う仕組み。セットの外壁に穴をあけ、ホストPC（部屋）の床にある金庫にケーブルで接続する。**セット（Container）を壊しても、金庫（データ）だけは手元に残り続ける**。
* **Port Mapping（専用インターホン）**
  * コンテナは外装（Namespace）で防音隔離されているため外から見えない。外の世界（ホストPC）のポートとコンテナ内部のポートを「インターホン」のように直結させ、外部からの通信を内部へ届ける。
* **Network（専用糸電話）**
  * コンテナ同士を安全につなぐ内線網。外部にポートを開放せずとも、同じ糸電話グループに属するセット同士だけで安全に通信が可能。

### ④ 運用・最適化ツール（Compose / Multi-stage Build / Registry）

* **Container Registry（3Dデータ共有サイト）**
  * Docker Hubなどに代表される、Image（3Dデータ）をアップロード・ダウンロード（`pull`/`push`）できるライブラリ。
* **Docker Compose（テーマパークの一括起動プラン）**
  * Webサーバー、DBサーバーなどの複数のセット（Container）、ネットワーク（糸電話）、ボリューム（金庫）の構成を1つの `docker-compose.yml` に定義し、一括で作成・稼働・停止を管理する。
* **Multi-stage Build（足場取り除き手法）**
  * コンパイルやビルドに必要な重い工具（開発ツール）を「作業用の足場」として使い、最終的な Image（3Dデータ）には完成品だけを載せることで、データ容量を大幅に軽量化する技術。

## 4. 普通のPC環境（非コンテナ）との比較

講座で「なぜDockerが必要なのか」を説明する際の比較ポイントです。

* **普通のPC環境（非コンテナ）**
  * 仕切りのない1つの大部屋の床に、直接パーツや配線（ライブラリや設定）を散らかして作業している状態。
  * **問題点:** アプリA用の部品とアプリB用の部品が混ざり、互いに干渉してシステムが故障する（環境汚染・依存関係の衝突）。
* **コンテナ環境（Docker）**
  * アプリごとに3Dプリントした個別パッケージのセット空間（Container）を用意し、その中で作業させる状態。
  * **メリット:** 各部屋が外装（Namespace）で完全に独立しているため、絶対に互いの部品が混ざらない。不要になったら部屋ごと廃棄すればホストPCは綺麗なまま保たれる。


## Dockerfile 主要命令（Instructions）の例え対応表

Dockerfile内に記述される1行ごとの命令（コマンド）は、**「セットの組み立て指示書に書かれたステップごとの具体的な作業指示」**に対応します。

| Dockerfile命令 | 3Dプリントセットでの例え | 技術的な役割・本質 |
| :--- | :--- | :--- |
| **`FROM`** | **「ベースとなる既成の部屋データ（土台）を指定する」** | ゼロから作らず、既存のBase Image（Linux OSなど）を土台として読み込む |
| **`WORKDIR`** | **「『これからの作業はセット内のこの部屋で行う』と指定する」** | 以降の命令（RUN, COPY等）を実行する作業ディレクトリを設定する |
| **`COPY` / `ADD`**| **「手元（PC）にある家具や小道具のデータをセット内に運び込む」** | ホストPC上のファイルやディレクトリを、Image内部にコピー配置する |
| **`RUN`** | **「セットに棚をネジ止めしたり、壁を塗装したりする（固定作業）」** | Imageを作成（build）する段階で実行し、パッケージ内に固定インストールする |
| **`ENV`** | **「セットの壁に『基本の注意事項ルール』をあらかじめ印字しておく」** | Image全体で共通して使われるデフォルトの環境変数を埋め込む |
| **`EXPOSE`** | **「セットの壁に『ここをインターホン用の穴にする』と印を入れる」** | ポート転送（Port Mapping）で使う予定のポート番号を文書上に明示する |
| **`VOLUME`** | **「セットの壁に『ここを外部金庫に繋ぐ接続穴にする』と指定する」** | マウントポイントとして機能させるディレクトリを指定・宣言しておく |
| **`USER`** | **「セット内で動く仕掛けの『操作権限（誰が動かすか）』を決める」** | セキュリティ対策のため、実行時のユーザー権限をルート（管理者）以外に変更する |
| **`CMD`** | **「セットを稼働させた瞬間（プリント後）に起動するデフォルトスイッチ」** | Container起動時に自動実行されるデフォルトのコマンド（上書き可能） |
| **`ENTRYPOINT`** | **「セットを稼働させたら『何があっても絶対に動かす固定メインモーター』」** | Container起動時に必ず実行されるメインコマンド（上書きされにくい） |

---

### 💡 特に重要な命令の解説と「RUN」と「CMD」の違い

初心者講座で最もつまずきやすいのが **`RUN`** と **`CMD`** の違いです。この例えを使うと一発で区別できます。

* **`FROM`（土台の選択）**
  * 「まっさらな部屋」から作るのではなく、「基本の洋館の部屋データ（`FROM ubuntu`）」や「調理場付きの部屋データ（`FROM python`）」など、**ベースとなる土台データを指定するスタート地点**です。
* **`RUN`（3Dデータに固定される建築・加工作業）**
  * **【build時に実行】** 3Dデータ（Image）を作成する最中に、壁に棚を取り付けたり（`apt-get install`）、塗装を行ったりする作業です。完成した3Dデータ（Image）の構造として**永久に固定・焼き付け**されます。
* **`CMD` / `ENTRYPOINT`（プリント後に動き出す仕掛けのスイッチ）**
  * **【run時に実行】** 3Dデータを作成している最中には動きません。プリントアウトされてセット空間（Container）が完成し、**電源スイッチ（`docker run`）を入れた瞬間に初めてカタカタと動き出す「仕掛け・からくり（Process）の初期動作」**です。
