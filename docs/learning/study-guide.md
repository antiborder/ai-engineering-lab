# AI Engineering Lab 学習ガイド

Fundamentals と GenAI Systems、全11ページを順番に進めるための学習ガイド。各ページで「何をするか」と
「そこで何がわかるようになるか」を、実際の画面構成（タブ・パイプライン・ステップ）に沿って書く。

推奨の進め方は上から順番:
Classical ML → Neural Networks → Transformers → Tiny LLM →
LLM API → Prompt Engineering → Structured Output → RAG → Tool Calling → Agents → Workflows

特に Transformers → Tiny LLM、Classical ML → Neural Networks の流れは「同じ仕組みが発展していく」体験になっている。

## Fundamentals — LLMの中身を理解する

### 1. Classical ML（`/fundamentals/classical-ml`）— 3つのタブ

**(a) Regression タブ — ガイド付き5ステップ**

- **Step 1: データを見る** — 最初は曲線を一切表示せず、点だけを見せる。「回帰とは、この点の並びから、新しい入力に対しても使える関数を見つけること」という目的をまず言葉にせず体で理解させるため。
- **Step 2: 学習前のモデル（最初の推測）** — 重みがすべてゼロの状態＝「何も知らない状態」を平らな直線として見せる。モデルは `ŷ = w₀ + w₁x + w₂x² + w₃x³` という3次多項式で、`wᵢ` がこれから学習される重みだと説明される。
- **Step 3: 誤差を測る** — 各点から直線までの縦の距離（赤い線）を見せながら、MSE（平均二乗誤差）の数式 `MSE = (1/n)Σ(ŷᵢ − yᵢ)²` を提示する。「誤差を2乗する＝プラスもマイナスも等しく罰し、大きな誤差ほど強く罰する」という設計意図がここでわかる。
- **Step 4: 1回だけ更新する** — 「Take one step」ボタンで、勾配降下法の更新式 `wᵢ ← wᵢ − η・∂MSE/∂wᵢ` を1回だけ実行する。ボタンを押した瞬間にカーブがわずかに動くのを見て、「学習＝この式を1回実行すること」だと体感できる。`η`（イータ）は学習率＝1回の更新でどれだけ大きく動くかを決めるパラメータ。
- **Step 5: 繰り返す** — 「Train 200 steps」で同じ更新を200回連続実行し、損失グラフが下がりながらカーブがデータの波形にフィットしていく様子を見る。「学習とは、Step 4の操作をひたすら繰り返すことに過ぎない」という結論に到達する。
- **自由探索（フリープレイ）** — Polynomial degree（多項式の次数）・L2正則化・ノイズ・train比率のスライダーを自分で動かせる。次数を上げすぎると訓練誤差は下がるのにテスト誤差は上がる＝**過学習**が起こることを、警告メッセージ付きで確認できる。

**(b) Classification タブ**

- **決定境界の可視化** — 2次元平面を色分けしたヒートマップで、「モデルがどこからどこまでを何色と判定しているか」を面として見せる。Regressionの「カーブ」が2次元では「境界の形」に対応する。
- **多項式次数と境界の形** — 次数を上げると、直線だった境界が曲がりくねった形を取れるようになる。Regressionでの「次数を上げると波打つカーブになる」と同じ現象が、分類問題では「境界線が複雑になる」という形で現れる。
- **train/test精度とoverfitting警告** — 訓練データへの精度とテストデータへの精度を並べて表示し、乖離が大きいと過学習の警告が出る。Regressionと同じ考え方を、数値（loss）ではなく精度（accuracy）で確認する形。

**(c) Clustering タブ**

- **教師なし学習という違い** — RegressionもClassificationも「正解ラベル」があったが、Clusteringにはない。点の座標だけを頼りに、似た点同士を自動でグループ分けする。
- **k-meansのアルゴリズム** — 各点を最も近い中心点（セントロイド）に割り当て → 各グループの中心点を再計算 → また割り当て直す、を繰り返す。1回のクリックが「1イテレーション」で、Regressionの「1ステップ」に対応する単位。
- **kの数と本当のグループ数** — 「探すクラスタ数（k）」と「実際のグループ数」を別々に設定できるので、kを少なくしすぎる（グループが混ざる）／多くしすぎる（1つのグループが分裂する）の両方を実験できる。

### 2. Neural Networks（`/fundamentals/neural-networks`）

- **アーキテクチャの選択** — 隠れ層の数（0〜2層）と活性化関数（tanh / ReLU）を選べる。「隠れ層なし」を選ぶと、実質Classical MLの線形分類と同じ表現力しかないことが確認でき、層を増やすほど境界が複雑になっていくのがわかる。
- **ネットワーク図** — 丸（ニューロン）と線（重み）で構成された図。線の色は重みの符号（正か負か）、太さは大きさ、丸の明るさはそのニューロンが平均的にどれだけ強く反応しているか（活性度）を表す。学習が進むにつれてこの図自体がリアルタイムで変化する。
- **決定境界（Classificationタブとの比較用）** — Classical MLのClassificationタブと全く同じ形式のヒートマップ。同じ問題を「1つの数式」で解いた場合と「ニューラルネット」で解いた場合を、意図的に同じ見た目で見比べられるようにしてある。
- **学習ループ（逆伝播）** — 見た目上はRegression/Classificationと同じ「損失が下がっていく」グラフだが、内部では逆伝播（誤差を出力層から入力層に向かって連鎖律で配分する計算）が行われている。層が増えるほど計算は複雑になるが、「損失を減らす方向に重みを動かす」というゴール自体はClassical MLと同一。

### 3. Transformers（`/fundamentals/transformers`）— 8段階のパイプライン

画面上部に **Text → Tokens → Embeddings → Q/K/V → Attention → Multi-Head Attention → FFN → Next Token** という8段階が常に表示されている。

- **Text → Tokens（トークン化）** — 入力した文章が単語・記号単位に分割され、チップとして表示される。
- **Tokens → Embeddings（埋め込み）** — 各トークンが数値ベクトルに変換される。同じ単語は常に同じベクトルになる（決定的）ことも確認できる。ここに位置エンコーディング（何番目のトークンかという情報）が足される。
- **Embeddings → Q/K/V** — 各トークンのベクトルが、Query（何を探しているか）・Key（何を持っているか）・Value（実際の中身）という3種類に変換される。
- **Q/K/V → Attention** — QueryとKeyの類似度を計算し、softmax（合計が1になるように変換する関数）を通して「注目の重み」にする。画面のヒートマップで、行（クエリ側のトークン）が列（キー側のトークン）をどれだけ見ているかが色の濃さでわかる。
- **因果マスキング** — ヒートマップの右上（未来のトークン）が暗い赤色で塗りつぶされているのが、「まだ生成していない未来の単語は見てはいけない」というルールの可視化。レイヤーやヘッドを切り替えても、この右上のマスクだけは常に同じ位置に出ることを確認できる。
- **Multi-Head Attention** — Head数を1〜8個の間で切り替えられる。複数のヘッドがあるということは、同じ文章に対して複数の「注目パターン」を同時に計算できるということ。
- **FFN・Transformerブロックの積み重ね** — 「Transformer blocks」の数（1〜3）を変えると、Attentionの計算が何回積み重なるかが変わる。ブロックが増えるほど、より複雑な文脈理解が理論上可能になる。
- **Next Token（未学習であることの意味）** — 最後に表示される次トークンの予測確率は、重みがランダムなままなのでほぼ意味を持たない。ここが「仕組みは本物だが、知能はまだ何もない」状態であることの証拠であり、次のTiny LLMで「学習させると何が変わるか」を対比させるための伏線になっている。

### 4. Tiny LLM（`/fundamentals/tiny-llm`）

- **アーキテクチャ設定** — Transformerブロック数・Attentionヘッド数・学習率を設定する。Transformersページと同じ構造のモデルだが、今回は本物のPyTorchコードがバックエンドで動く。
- **学習（Train）** — ボタンを押すたびに実際の勾配降下法が数十〜数百ステップ走り、損失グラフが下がっていく。裏側では「予測 → 損失計算 → 逆伝播 → 重み更新」というNeural Networksページと同じループが、文字単位のテキストデータに対して回っている。
- **生成（Generate）** — プロンプトを与えると、1文字ずつ予測しては入力に追加する、という**自己回帰生成**が行われる。学習前は完全なランダム文字列だが、数千ステップ学習させると、実在する単語や、学習データにあるフレーズに近い文章が生成されるようになる。
- **温度（Temperature）** — 生成のランダムさを調整するパラメータ。低くすると「最も確率の高い文字」ばかり選ぶ手堅い生成に、高くすると多様だが崩れやすい生成になる。

## GenAI Systems — LLMアプリケーションを作る

### 1. LLM API（`/genai/llm-api`）

- **System prompt / User prompt** — 「振る舞いの指示（system）」と「本題の質問（user）」という2つの入力欄があり、これがLLM APIの最も基本的な呼び出し形式であることを示している。
- **Call details（呼び出しの計測）** — 1回の呼び出しごとに、入力/出力トークン数・レイテンシ（応答にかかった時間）・推定コストが表示される。実運用のLLMアプリでは、この4つの数値を常に監視することになる。

### 2. Prompt Engineering（`/genai/prompt-engineering`）

- **Prompt A / Prompt B** — 2つの異なるsystem promptを並べて設定する。
- **共通テストケース** — 同じ質問リストを両方のプロンプトに流す。「条件を揃えて比較する」という実験の基本がここにある。
- **並列比較結果** — 同じ質問に対する2つの回答が左右に並び、平均レイテンシ・平均トークン数も比較できる。プロンプトの言葉選び一つで、答えの長さやトーンがどれだけ変わるかを直接見比べられる。

### 3. Structured Output（`/genai/structured-output`）

- **JSON Schemaエディタ** — 「name は文字列、age は整数」のような出力の型を自分で編集できる。
- **Generate（生成）** — 編集したスキーマに沿った形の出力が生成される。
- **Validation（検証）** — 生成された出力が本当にスキーム通りかを自動チェックし、合格/不合格を表示する。
- **deliberately break the output（わざと壊す）** — チェックを入れると、意図的にスキーマ違反のデータを生成させ、バリデーションが実際にエラーを検出する様子を確認できる。「検証が本当に機能している」ことの証明。

### 4. RAG（`/genai/rag`）— 10段階のパイプライン

画面上部に **Document → Parsing → Chunking → Embedding → Vector Search → Top-K → Reranking → Context → LLM → Answer** という10段階が表示されている。

- **Document（文書管理）** — 6件のデモ文書が最初から入っており、自分で文書を追加・削除することもできる。
- **Chunking（チャンク分割）** — 文書を「Chunk size（何語ずつ区切るか）」「Overlap（隣接チャンクをどれだけ重ねるか）」で細切れにする。小さすぎると文脈が失われ、大きすぎると無関係な情報が混ざる。
- **Embedding → Vector Search（ベクトル検索）** — 各チャンクと質問文が数値ベクトルに変換され（本物のTF-IDFという手法を使用）、質問ベクトルに近いチャンクほど検索結果の上位に来る。スコアは見せかけではなく実際に計算された類似度。
- **Top-K / Similarity threshold** — 検索結果を何件まで使うか（Top-K）、どのくらい類似度が低いものまで許容するか（threshold）を調整できる。
- **Reranking（再順位付け）** — オンにすると、ベクトル類似度に加えて「質問の単語がチャンクにそのまま含まれているか」も加味した2段階目の並べ替えが行われ、順位が変わることがある。
- **Context → LLM → Answer** — 選ばれたチャンクがまとめて1つの文脈（コンテキスト）としてLLMに渡され、それだけを根拠に回答が生成される。パラメータを変えるたびに、この最終回答も変わることを確認できる。
- **Save as AI Artifact** — 今の設定（chunk size, top-K, rerankingの有無など）に名前を付けて保存すると、それがアプリ全体で共有される「1つの資産（Artifact）」になり、以降Evaluate/Optimize/Deployボタンから他のモジュールに引き継がれる。

### 5. Tool Calling（`/genai/tool-calling`）— 7段階のパイプライン

**User → LLM → Tool Selection → Tool Execution → Tool Result → LLM → Answer**

- **Tool Selection（ツール選択）** — メッセージの内容（計算式か、「weather in ○○」か、それ以外の質問か）を見て、電卓・天気・文書検索のどれを使うか、あるいは何も使わないかが決まる。
- **Tool Execution → Tool Result** — 選ばれたツールが実際に実行され、その結果（例:「15% of 240 → 36」）がそのまま画面に表示される。
- **LLM → Answer** — ツールの結果を踏まえて、最終的な回答文が組み立てられる。「LLM単体では計算できないことも、ツールと組み合わせれば正確にできる」という価値がここでわかる。

### 6. Agents（`/genai/agents`）

- **Plan（計画）** — 1つのゴール（例:「東京の天気を調べて、850の12%も計算して」）が与えられると、必要なツール呼び出しのリストにまず分解される。Tool Callingが「1回きりの選択」だったのに対し、ここでは複数ステップの計画が立てられる。
- **Execution trace（実行ログ）** — 計画の各ステップが順番に実行され、それぞれの結果（Observation）が記録される。失敗したステップには「retried」というラベルが付き、1回だけ自動的にやり直されることも確認できる。
- **Final answer（最終回答）** — すべてのステップの結果を踏まえて、ゴール全体に対する1つの回答がまとめられる。途中の「考え方」そのもの（内部の思考過程）はあえて見せず、計画・実行・結果だけが表示される設計になっている。

### 7. Workflows（`/genai/workflows`）

- **Deterministic Workflow（決定的ワークフロー）** — 入力の内容に関わらず、常に同じ2ステップ（検索してから答える）を実行する。
- **Agentic Workflow（Agentic ワークフロー）** — 同じ入力に対して、Agentsページと同じ仕組みで、内容に応じた計画を動的に立てて実行する。
- **左右比較** — 数式の質問を入れると、決定的ワークフローは無関係な文書を検索してしまう一方、Agentic側はちゃんと電卓を選ぶ。ただし画面下の注釈にもある通り、「決定的ワークフローの方がシンプルで安く、動作も完全に予測可能」というトレードオフも同時に強調されており、「Agentが常に優れているわけではない」という結論に導かれる。
